Claim and result
  "Browser Use configuration supports rules for those two schemes, and setting
  access to allow still leaves the tool's other policy checks in force."

  The schemes were not named. Testing establishes that this statement is true
  for HTTP and HTTPS, but false for file and data in the installed browser bundle.
  The CLI accepting a configuration key does not establish browser support.

  Native config/read preserves http://example.com, https://example.com,
  file://*, and data:* origin keys. Upstream models origins as a map with string
  keys in codex-rs/config/src/browser_use.rs and the app-server protocol.

  In the installed browser service, the independent navigation predicate $x
  uses Object.freeze(["http:","https:"]) and an exact about:blank exception.
  hS and bS accept only HTTP/HTTPS origins and patterns. Invalid patterns are
  ignored. xM resolves origin policy separately; pi makes deny win over allow.
  RZ retains network policy checks and reports unavailable requirements.
  These minified symbols are specific to the fingerprint above.

  Both live Browser Use goto calls were rejected before navigation:
    data:text/plain,CODEX_SCHEME_PROBE
    file:///.../probe.html (an agent-created, harmless test file)
  Reason: navigation_url_policy_blocked; allowed protocols: http:, https:.

  The unchanged policy functions passed 21 executable checks, covering matching,
  managed denies, network denies, unavailable requirements, upload/download/CDP
  restrictions, invalid protocols, and the exact about:blank exception.
  scripts/verify-installed-browser-policy.cjs reproduces these checks without
  executing browser/network APIs or changing the service. It requires the exact
  known bundle hash and rejects an unknown version rather than guessing.

Configuration implications
  Supported examples in CODEX_HOME/config.toml:

    [browser_use.origins."http://example.com"]
    access = "allow"

    [browser_use.origins."https://example.com"]
    access = "allow"

  These are exact origins and separate protocol/port matches. They can override
  a user default deny for that origin; they cannot override a managed deny.
  Unset access already defaults to allow. Allow is not an automatic browser
  approval and does not remove site, capability, saved-permission, or review
  checks. No working config-only change adds file/data navigation to this bundle.
  No edits were made to the user's active config or the browser plugin.

Validation limits
  Local package probes used the existing September 26 binaries; they are not a
  claim that a new full Codex release has been compiled or published. The new
  Windows build requires debug commands to be visible in the built executable.
  Source patches and release gates do not make arbitrary schemas, protocols,
  unknown methods, or server-rejected calls valid. Browser support belongs to
  the separately installed service, not to the Windows sandbox patch.
